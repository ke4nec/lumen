# P4：视觉与性能验收

初次被测源码 `a45ebd6`；CPU 最终测量为该提交加本阶段的 `compositePixel` 内联修复，报告标为 `a45ebd6+P4-inline`。Skia 光栅测量继续使用已保存、核对 SHA256 的 P3 二进制；这项 CPU 私有函数修改不在 Skia 光栅调用链中。before 二进制来自 P0 冻结目录，开始前逐项复核 SHA256 与 P0 归档一致。CPU-only 与 Skia raster 分开配对，所有运行顺序执行，不并行构建、渲染或图像批处理。

## 全链路 review

文件解码显式 Straight；ResourceManager 保存模式和恢复原图；两个 CPU 接纳入口归一化一次，draw 只读取缓存。CPU source-over 没有输出 alpha 除法。Skia 两后端按输入模式上传；raster 输出实际预乘格式，GPU 生产源码没有逐帧读回。v7 写入固定宽度模式，v6 输入按 Straight 解释；错误解码不覆盖调用方命令。

完整清屏建立 Opaque 证明，透明/半透明清屏保持 Premultiplied，Preserve 与双缓冲同步模式。清屏色或 DPI 变化使旧配置不可复用，但不丢弃已发布帧。SDL present 只检查结构，正常透明/不透明帧均直接提交；兼容分支复用 scratch，回到直接路径后释放。Gallery 仅在导出时生成直通副本。

核对到计划对 `pixels()` 的“始终已完成帧”措辞过宽：既有 CPU API 在首个完成帧前允许读当前即时缓冲，P2 保留这一兼容行为并有回归；首帧完成后所有读取均为上次完成帧。计划已补上这一明确例外，未把配置失效变成暴露未完成缓冲的理由。

初轮 CPU edges 第三组 submit p95 比 P0 增加 14.26%，没有直接通过门槛。MSVC Release 汇编显示半透明像素通过非内联 `compositePixel` 调用、重复传递七个参数；本阶段对该私有标量函数强制内联，保留唯一一套整数公式和现有几何。修复后的 Release 对象已无该函数调用，edges 原始帧与 P3 逐字节相等。CPU 所有场景重新进行三组完整配对，初轮只作排查证据。没有引入 SIMD、线程或新的采样方法。

采样 review 发现个别窗口被缩小或最小化：请求 4K 的实际 drawable 可能是 3840×1100，另有 160×28 的样本。此类报告不作为性能证据；整对重新采样。驱动与汇总均检查最终 drawable 等于请求尺寸，Windows 驱动另在外部线程每 200 ms 观察客户端尺寸/最小化状态，异常时拒绝报告。before/after 使用同一观察方式。

图像工具改为标准库的逐通道字节处理，降低完整矩阵的运行成本；与 P0 工具核对 48 个尺寸/模式/精确与容差组合，所有 PNG 和差异 JSON 逐字节相等，并检查非法模式/内容拒绝。整数公式、棋盘、误差放大与 P0 冻结容差均未改变。

## 采样与证据

沿用 P0 的 warmup=30 / frames=300、每后端 15 个场景/呈现组合、三组相邻 before/after 配对；偶数组交换先后顺序。没有重建 before、修改旧场景、扩张 RGB 容差或更新既有控件 golden。测量命令见统一命令表 §4；汇总工具 `benchmarks/compare_alpha_baseline.py` 保留各组 p50/p95、分配/内存字段与超过 10% 的待审项，不能自动把超限判为噪声。

CPU 第三组首次运行被 20:01 合盖睡眠中断，20:22 系统恢复并记录电源事件；驱动 timeout，没有完成的报告不计入结果。该组全部旧记录移至 `build-alpha-after/p4-paired/interrupted-group3`（含 Windows Kernel-Power 事件），恢复后整组重新交错采样。新增 `--resume` 只保留完整相邻配对，先核对 revision、二进制 SHA256、CMakeCache 和命令/参数，半对必须两端重跑。前两组完整样本保留，组间绝对时间受电源/频率状态影响，结论以组内配对和完整波动范围为依据。

历史 M0 `v0.2-cpu-scene.json` 为 Linux/GCC 15.2.0，当前为 Windows/MSVC 1950，不能直接计算回归率。250 nodes、769 commands、322 culled、270 partial frames 与当前前后报告相同；M0 哈希 `d28e364efe1b4aca` 在迁移前 P0 已为 `26782f10603a53fe`，不把这项既有跨环境差异归因于本次 alpha 改造，也不改写历史文件。

最终 review 还修复了断点恢复的配对原子性：整对重跑时，先写 `.pending`，只有两端均成功才删除；否则旧 JSON 与新 JSON 可能混成一对。比较工具拒绝尚有该标记的目录。模拟第二端失败的回归检查确认：即使两个 JSON 都存在，恢复仍重跑两端；完成后再次恢复不启动进程。对最终 CPU 数据实际执行 `--resume`，45 对全部保留、未重新采样。日志为 `build-alpha-after/p4-checkpoint-regression.log` 和 `build-alpha-after/p4-resume-verify.log`。

## 宿主提交的定向诊断

`lumen-alpha-present-probe` 只提交不变的 1080p 像素，不执行渲染。Straight R=255/A=128 与 Premultiplied R=128/A=128 表示同一颜色；Windows native software、透明窗口、vsync 请求关闭，每次 warmup=30 / frames=300，三组交错运行。`--period-ms 40` 将等待放在 present 计时外，`--period-ms 0` 连续提交。尺寸变化、最小化或超过 5 秒的采样中断直接失败。

固定 40 ms 间隔的 host p95，三组分别为 3331.8→3606.4、3509.3→3666.7、3114.2→3418.9 µs（+8.2%、+4.5%、+9.8%）；p50 配对变化 +4.5%、+8.2%、+24.6%，第三组绝对增加 497.7 µs。连续提交的 host p95 则为 1975.1→1752.9、3209.7→1853.1、3603.0→1794.5 µs。相同预乘输入，仅改变提交间隔就使 host p50 的组三次中位数由 930.7 变为 2557.0 µs。

此实验说明 host 调用对提交节奏敏感，支持将宿主耗时和格式准备分开分析；它不证明正式窗口配对中的每个波动都由同一原因造成，也不替代包含渲染的正式配对。源码检查该路径仍执行相同的 surface blit/update，直接路径只是省去前置 alpha 转换。原始数据在 `build-alpha-after/p4-inline-check/present-*.json`，包含实际观察到的窗口尺寸。

正式 CPU 1080p software 不透明场景的原始帧 before/after 均为 FNV `97289e6761c49fdc`，字节相同，转换计数均为零；host p95 的配对中位仍增加 12.74%，不能省略。补充 `--host opaque` 控制：固定 40 ms、完全相同 R=128/A=255 输入，只切换 Straight/Opaque 标记，host p95 三组 2340.6→2503.1、2538.1→2384.2、2456.5→2389.8 µs（+6.9%、-6.1%、-2.7%），均零转换和 scratch，没有稳定的模式分派成本。

同一 Opaque 输入把间隔从 30 ms 改为 18 ms，host p95 变为 2473.0→2833.3、2354.8→2512.2、2547.2→2578.8 µs（+14.6%、+6.7%、+1.2%）。这复现了“渲染更快、提交间隔缩短时，宿主分项可能变长”的现象；并未精确归因每一次系统调度波动。正式 CPU 软件呈现的全部 host 超限仍列在 JSON；各窗口 total 三组均改善，模式处理没有新增转换或不透明路径的像素遍历。

| headless 场景 / 计时段 | 三组配对变化中位数 p50 / p95 | 审查 |
| --- | --- | --- |
| card-grid / paint | +0.78% / -0.39% | 无显著变化 |
| text-heavy / paint | +3.55% / +3.26% | 原始第三组异常，追加核查见下 |

全部诊断见 [P4-controls.json](P4-controls.json)：98 次后续运行、12 次原始透明呈现探针，以及内联修复前的边缘数据。A/A 的两个标签使用完全相同的可执行文件；归档脚本核对 SHA256、帧哈希、场景和参数一致。它们用于判断重复测量的分辨能力，没有替换正式结果或删掉异常组。

- **edges**：正式 p95 为 +24.8%、+20.0%、-4.7%；另三组原始 before/after 配对为 +9.4%、-10.2%、+11.4%，p50 为 -4.4%、-3.5%、+4.4%。相同二进制 A/A p95 为 +5.7%、+25.0%、-35.1%。超限没有稳定复现，当前主机不足以将这些尾部差异归因为 Skia 代码变慢。
- **上传**：正式 Skia `alpha-upload` 的 upload p50 增加 25.7%–58.0%；追加三组配对变为 -2.5%、-61.1%、-54.1%。同一二进制 A/A p50 也出现 +81.2%、+50.2%、-6.3%，排除了“原始增加必然来自新增模式验证”的归因。没有像 CPU 那样额外执行归一化循环，不宣称 Skia 上传变快或变慢。
- **text-heavy**：正式第三组 paint p50/p95 增加 41.8%/50.2%，同时未改动的 layout p50 增加 55.4%，其余两组 paint p95 为 -2.2%/+3.3%。三组 A/A paint p95 为 +2.1%、+2.5%、+0.6%；明确追加的第四对旧/新二进制为 p50 370717.5→375179.7 µs（+1.2%），p95 422946.6→414519.0 µs（-2.0%）。没有复现原始异常；未能精确追溯当时主机调度/频率原因，原记录仍保留，不刷新基线掩盖它。
